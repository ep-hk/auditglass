# The demo

```bash
auditglass demo
```

No backend, no credentials, no API key, no model download. The whole pipeline runs —
policy, templates, provider, redaction, planning, reasoning, audit — against a
synthetic incident, and writes a real run directory.

A committed copy of that output is at [`../examples/run-sample/`](../examples/run-sample/)
if you would rather read it than run it.

## The incident

```
payments p99 latency degrades
  └─> orders holds its connections open longer waiting on payments
        └─> orders' connection pool saturates
              └─> orders returns timeouts, which is what alerts
```

**It is deliberately not solvable in one query.** Round one sees timeouts and cannot say
why. Round two sees the saturated pool and asks what `orders` depends on. Round three
finds the latency in `payments`. Each round depends on what the previous one returned —
which is the thing the tool exists to do, and the thing a single hand-off to an ops team
cannot do.

`inventory-db` is also a declared downstream of `orders`, and it is healthy. It is there
so that "which downstream?" is a real question with a wrong answer available, rather
than a single obvious one.

Watch it fail without the rounds:

```bash
auditglass demo --max-rounds 1
```

There is a CI job asserting this stays true. If the incident ever becomes solvable in
one query, the premise of the project is visibly false to anyone running the demo.

## Other things to try

```bash
auditglass demo --simulate-outage    # metrics backend down: reports its evidence gaps
auditglass templates --config src/auditglass/_demo/config.yaml
auditglass policy    --config src/auditglass/_demo/config.yaml
```

The last two print the complete set of queries the demo can make and the complete
egress allowlist. In a real deployment those two commands are how you check what you
have configured.

## What is planted in the fixture, and why

| Planted | Where | Why |
|---|---|---|
| A JWT in a log line | `orders` error at index 6 | Log hygiene failures are common, and secrets must not reach a model |
| A Luhn-valid card number and an email | `orders` error at index 11 | Something real for the detection rules to catch |
| Repeating client addresses | throughout | So pseudonymisation visibly preserves correlation |
| An injection payload | `orders` error at T+12.5 | To show the marker firing and the report rendering it inert |

The injection payload contains instructions addressed to an AI system and a Markdown
image pointing at an attacker-controlled URL. Look for it in the report's
"Instruction-like content" section, and note that the `![` sequence is escaped so no
client fetches that URL — while `evidence/E1.json` keeps the record verbatim, because
that is the forensic source of truth.

## Provenance

Everything is generated by [`generate_fixture.py`](generate_fixture.py) and is
entirely invented. Addresses are RFC 5737 documentation ranges, domains are RFC 2606
reserved names, and the card numbers are Luhn-valid but belong to no issuer's live
range and to no person. No production system is described by any of it.

```bash
python demo/generate_fixture.py     # regenerate; CI checks the committed copy matches
```
