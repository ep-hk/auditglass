## 0. 一句话定位

> **Incident forensics for engineers who don't have production access.**
> 事故取证，给没有生产权限的工程师。

不是 AIOps 平台，不是告警降噪，不是自动修复。是在职责分离约束下，替代人执行多轮只读取证的受控组件。

---

## 1. 背景与问题陈述

### 1.1 现状

在实施职责分离（Segregation of Duties, SoD）的组织中——银行、保险、医疗、政府、上市公司的受监管系统——应用工程师依照合规要求**不具备生产环境访问权限**。

生产事故发生时的典型流程：

1. 告警触发，值班工程师被叫起
2. 工程师无法直接查看生产日志 / 指标 / 追踪
3. 需通过运维团队或工单系统请求取证
4. 运维按请求捞取，返回结果
5. 工程师分析后发现需要另一组证据，回到第 3 步
6. 循环若干轮

### 1.2 问题

- **MTTR 被取证往返显著拉长**，而每一轮往返都发生在事故进行中
- 最了解系统的人拿不到一手证据，判断建立在二手转述上
- 现有的 AIOps / LLM 运维工具**几乎全部默认调用方具备生产访问权限**，在 SoD 环境下无法部署
- 组织若为提速而放宽访问控制，则直接违反合规要求

### 1.3 机会

取证本身是**只读**操作。若能让一个受控的自动化组件代替人执行"多轮取证 + 关联分析"，且该组件的写操作能力在多个独立层面被阻断、并留下完整可审计的痕迹，则可以在**不放宽访问控制**的前提下大幅压缩诊断周期。

### 1.4 何时**不**适用

主动划出边界，避免错误采用：

| 情况 | 建议 |
|---|---|
| 组织没有 SoD 约束，工程师本可获得生产只读权限 | 直接给权限，更简单也更快 |
| 可观测性后端不提供只读 API | 本工具无法工作（见 ASM-1） |
| 组织不接受任何形式的 LLM 参与事故处理 | 本工具的核心即为此，不适用 |
| 期待自动修复或自愈 | 见 N1，本项目永久不做 |
| 需要告警聚合、降噪或事件管理 | 见 N2，请使用成熟产品 |

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 衡量方式 |
|---|---|---|
| G1 | 在无生产写权限的前提下完成多轮自动取证与关联分析 | 端到端示例可在只读凭据下跑通 |
| G2 | 写操作能力在三个独立层面被阻断，不依赖模型行为 | 三层控制均有测试覆盖；越权调用在出站前被拒 |
| G3 | 每次诊断产出可审计、可还原的完整记录 | 审计记录可还原全部查询与推理输入输出 |
| G4 | 敏感数据在离开组织边界前完成伪名化，且保留关联性 | 伪名化在 LLM 调用前执行；同值同 token；有命中记录 |
| G5 | 支持数据完全不出域的部署模式 | 可对接本地模型端点，无出网容器中可跑通 |
| G6 | 第三方可在不修改核心代码的前提下接入自有后端 | 有 connector 开发文档 + 至少一个社区实现 |
| G7 | 模型不生成查询语句，仅从受约束模板中选择并填参 | 无模板外查询可被表达；有对抗测试覆盖 |

### 2.2 非目标（明确不做）

| # | 非目标 | 理由 |
|---|---|---|
| N1 | **不执行任何修复动作**（重启、扩容、回滚、改配置） | 一旦具备写能力，整个合规叙事失效。此项永久有效 |
| N2 | 不做告警聚合 / 降噪 / 事件管理平台 | 已有成熟产品，非本项目差异化所在 |
| N3 | 不做可观测性数据的采集与存储 | 对接既有后端，不与之竞争 |
| N4 | 不替代人的决策 | 产出是诊断报告，结论由工程师判断 |
| N5 | v0.1 不做 Web UI | CLI + 报告文件即可验证核心价值 |
| N6 | 不做多租户 SaaS | 目标用户要的是自托管 |
| N7 | 不主张单靠本工具即可保证只读 | 见 §6.1，只读依赖部署方的最小权限凭据为主控 |

## 3. 目标用户

| 画像 | 角色 | 核心诉求 | 决定是否采用的关键点 |
|---|---|---|---|
| **P1 值班工程师** | 受监管企业的应用/平台工程师 | 事故中更快拿到证据 | 五分钟能否跑起来；报告是否可直接用 |
| **P2 SRE / 平台负责人** | 引入决策者 | 提升 MTTR，不引入新风险 | 只读保证是否可信；能否对接现有后端 |
| **P3 安全 / 合规官** | 否决权持有者 | 不扩大攻击面，可审计 | 威胁模型、审计记录、数据是否出域 |
| **P4 内部审计** | 事后追溯 | 证明 AI 在事故中做了什么 | 记录是否完整、可还原 |

> **P3 拥有否决权**，是采用链路上的真实瓶颈。大量设计取舍（三层只读控制、模板化查询、威胁模型文档、本地模型支持、仓库内样例 run 目录）都是为了让 P3 能够批准试用。

## 4. 用户故事

**US-1**｜作为值班工程师，当告警触发时，我希望自动收到一份包含相关日志、指标异常点与初步判断的报告，而无需逐轮向运维请求取证。

**US-2**｜作为值班工程师，我希望报告中的每一条结论都标注它依据的证据编号，以便我自己复核而不是盲信。

**US-3**｜作为平台负责人，我希望在不修改核心代码的前提下接入我们自有的日志后端。

**US-4**｜作为安全官，我希望能够验证写操作在技术上被阻断，而不是依赖"我们提示它不要这么做"；并且希望知道每一层控制失效时会发生什么。

**US-5**｜作为合规官，我希望敏感数据在发送给外部模型之前被伪名化，并且可以选择完全使用本地模型使数据不出域。

**US-6**｜作为内部审计，我希望对任一历史事故，能还原 agent 执行过的全部查询、取回的证据与推理过程。

**US-7**｜作为潜在贡献者，我希望在不接触任何真实生产系统的情况下跑通测试并提交 PR。

**US-8**｜作为安全官，我希望即使生产日志中被植入了针对 AI 的指令内容，agent 也不会因此查询声明范围之外的数据。

**US-9**｜作为值班工程师，当部分后端在事故期间不可用时，我希望仍拿到报告，并清楚知道哪些证据没能取到。

## 5. 功能需求

优先级：**P0 = v0.1.0 必须有**｜P1 = v0.2 目标｜P2 = 待定

### 5.0 核心抽象

系统由七个可替换抽象构成，全部为接口（FR-7.1）：

| 抽象 | 职责 |
|---|---|
| **Trigger** | 接收诊断请求，产出标准化的 incident context（服务、时间窗、告警负载） |
| **Planner** | 决定下一轮取什么证据；持有作用域与预算；可为规则式或 LLM 驱动 |
| **PolicyGuard** | 中介全部出站调用，默认拒绝 |
| **EvidenceProvider** | 对接具体后端，执行受约束查询，返回标准化证据 |
| **Redactor** | 在证据进入 Reasoner 之前完成伪名化与标记 |
| **Reasoner** | 依据证据产出结构化结论 |
| **AuditSink** | 落地 run 目录与全部审计产物 |

> Planner 与 Reasoner 分离是刻意的：安全关键决策（作用域、预算、模板选择）集中在 Planner，可独立测试；且允许**无 LLM 的规则式 Planner**，使快速开始不依赖任何 API key 或模型下载。

### 5.1 触发（Trigger）

| ID | 需求 | 优先级 |
|---|---|---|
| FR-1.1 | 支持 CLI 手动触发，指定时间窗与关注服务 | P0 |
| FR-1.2 | 支持从文件或 stdin 读取标准告警负载：`agent run --alert-payload alert.json` | P0 |
| FR-1.3 | 触发源可插拔，新增无需修改核心 | P0 |
| FR-1.4 | 提供 Webhook 接收服务 | P1 |
| FR-1.5 | 支持轮询式触发（可配置间隔与数据源） | P1 |
| FR-1.6 | 内建 Jira / ServiceNow / Slack / PagerDuty 触发源 | P1 |

> FR-1.4 由 P0 降为 P1：运行 HTTP 服务引入认证、TLS、部署与攻击面，而 FR-1.2 的文件适配器已能覆盖全部价值——需要 webhook 的组织可用既有 ingress 包一层。

### 5.2 策略与只读强制（PolicyGuard）

| ID | 需求 | 优先级 |
|---|---|---|
| FR-2.1 | 所有出站调用必须经 PolicyGuard 授权，**默认拒绝** | P0 |
| FR-2.2 | 主机、路径、方法三元组允许清单，由配置文件显式声明 | P0 |
| FR-2.3 | 后端访问统一经受约束的 HTTP client；CI 断言代码库中无其他 HTTP 客户端被引入 | P0 |
| FR-2.4 | 对渲染后的查询语句执行校验（纵深防御；校验对象为模板生成的字符串，非模型自由文本） | P0 |
| FR-2.5 | 每一次拒绝写入审计记录，含原因与被拒调用的完整描述 | P0 |
| FR-2.6 | 策略配置支持版本化与哈希，记入 run manifest | P0 |
| FR-2.7 | 支持声明进程级出网允许清单，便于容器网络策略对齐 | P1 |
| FR-2.8 | 按角色 / 时间窗 / 数据敏感级的细粒度策略 | P2 |

### 5.3 受约束查询（Query Templates）

> 本节为 v0.2 新增。核心决策：**模型永远不生成查询语句。**

| ID | 需求 | 优先级 |
|---|---|---|
| FR-3.1 | 查询以参数化模板声明；模型输出为 `{template_id, params}`，渲染由代码完成 | P0 |
| FR-3.2 | 模板参数类型受限：枚举取值来自配置（如服务名），时间窗有上限且必须与事故窗口相交，结果条数有上限 | P0 |
| FR-3.3 | 单次运行的可触达数据集集合在运行开始时冻结；模型可收窄作用域，**不可放宽** | P0 |
| FR-3.4 | 审计记录同时保存 `{template_id, params}` 与渲染后语句 | P0 |
| FR-3.5 | 支持 `raw_query` 逃生口，**默认关闭**；开启时在报告与审计中显著标记 | P1 |

模板声明示例：

```yaml
# query-templates/loki.yaml
- id: logs.by_service_level
  backend: loki
  description: 按服务与日志级别取日志
  params:
    service:  { type: enum, source: config.services }
    level:    { type: enum, values: [error, warn, info] }
    window:   { type: timerange, max: 6h, must_intersect: incident_window }
    limit:    { type: int, max: 5000 }
  render: '{app="{{service}}"} | json | level="{{level}}"'
```

### 5.5 脱敏与伪名化（Redactor）

| ID | 需求 | 优先级 |
|---|---|---|
| FR-5.1 | **在数据送入 Reasoner 之前**执行处理 | P0 |
| FR-5.2 | 采用**确定性伪名化**而非掩码：同一值在同次运行中映射到同一稳定 token（`203.0.113.47 → IP_a37f2b1c`），保留关联性 | P0 |
| FR-5.3 | Token 生成为 `PREFIX + HMAC(run_salt, normalised_value)[:8]`；盐粒度可配置（默认每次运行一个盐） | P0 |
| FR-5.4 | 反查表仅存于本地 run 目录，可配置为不落盘 | P0 |
| FR-5.5 | 结构化日志默认走**字段级允许清单**；自由文本字段再走模式扫描 | P0 |
| FR-5.6 | 内建规则：邮箱、IP、账号类数字串、身份标识、金额 | P0 |
| FR-5.7 | 支持自定义正则与实体规则集 | P0 |
| FR-5.8 | 记录命中的规则与位置，**不记录原始值** | P0 |
| FR-5.9 | 处理失败时中止运行而非降级放行。"失败"定义为：规则引擎抛错，或 `strict_fields: true` 下遇到字段策略未覆盖的字段 | P0 |
| FR-5.10 | 对命中指令样式的证据块打**注入嫌疑标记**（标记，不拦截），标记进入报告与审计 | P0 |

**盐粒度取舍**（须在文档中明示）：

| 粒度 | 优点 | 代价 |
|---|---|---|
| 每次运行（默认） | 跨运行不可关联，隐私更强 | 无法做跨事故的模式分析 |
| 每个部署 | 支持跨运行关联 | 盐若泄漏，低熵值（IP、短账号）可被暴力反推 |

**局限声明（FR-5.11，P0）**：文档必须明确说明，伪名化是**数据最小化措施，不是保证**；要获得数据不出域的保证，唯一途径是 §5.7 的本地模型部署模式。同时说明非拉丁字符与多语言场景下规则覆盖的已知局限。

### 5.6 规划（Planner）

| ID | 需求 | 优先级 |
|---|---|---|
| FR-6.1 | 提供**规则式 Planner**，无需 LLM 即可执行完整流程（用于快速开始与测试） | P0 |
| FR-6.2 | 提供 LLM 驱动 Planner，输出受 §5.3 模板约束 | P0 |
| FR-6.3 | 持有并强制作用域与预算（查询次数、数据量、token、货币成本） | P0 |
| FR-6.4 | 循环终止条件明确：证据充分 / 预算耗尽 / 连续 N 轮无新证据。任一情况下均产出报告并标注终止原因与覆盖度 | P0 |
| FR-6.5 | 后端超时或不可用时继续执行，不中止整次运行 | P0 |
| FR-6.6 | 全局并发上限；按 (服务, 时间窗) 指纹合并同源触发，防止告警风暴放大后端负载 | P0 |

### 5.7 推理（Reasoner）

| ID | 需求 | 优先级 |
|---|---|---|
| FR-7.1 | 支持 Anthropic API 与 OpenAI 兼容端点（后者覆盖 vLLM 与 Ollama，数据可不出域） | P0 |
| FR-7.2 | 取回的数据在上下文中以显式边界标记包裹，声明为不可信输入（**辅助措施**，非主要防线；主要防线为 §5.3 的模板约束） | P0 |
| FR-7.3 | 输出受结构化 schema 约束，不接受自由文本触发动作 | P0 |
| FR-7.4 | 每条结论必须引用证据 ID，无引用的结论标记为推测 | P0 |
| FR-7.5 | 模型名与版本记入 run manifest | P0 |
| FR-7.6 | 单次运行的货币成本上限，执行前预估，超限硬停 | P0 |

### 5.8 审计与报告（AuditSink）

| ID | 需求 | 优先级 |
|---|---|---|
| FR-8.1 | 每次运行生成独立 run 目录，含 manifest / evidence / prompts / redactions / report | P0 |
| FR-8.2 | manifest 记录：触发源、时间、配置哈希、策略版本、模板集版本、模型版本、预算与实际消耗 | P0 |
| FR-8.3 | 完整记录每次 LLM 调用的输入与输出 | P0 |
| FR-8.4 | 产出人类可读的 Markdown 报告 | P0 |
| FR-8.5 | 报告含**独立的"证据缺口"章节**，列出未能取到的证据与原因 | P0 |
| FR-8.6 | 报告渲染中和证据内容：转义 Markdown、禁止自动渲染外链图片（防止经由 Slack/Markdown 查看器的外带信道） | P0 |
| FR-8.7 | 审计记录与**报告**中均不出现未经处理的敏感数据 | P0 |
| FR-8.8 | 同时产出机器可读的 JSONL | P0 |
| FR-8.9 | **记录还原**：从 run 目录完整还原执行了哪些查询、取回了什么、送入模型的是什么、模型返回了什么 | P0 |
| FR-8.10 | run 目录保留期可配置，提供 `agent purge` 清理命令 | P0 |
| FR-8.11 | 输出目标可插拔（本地、S3、SIEM、syslog） | P1 |
| FR-8.12 | **固件重跑**：以记录的证据为 fixture 重新执行流程，用于回归测试。模型输出不保证逐字一致 | P1 |

> v0.1 的 FR-6.7"确定性重放"在本版拆为 FR-8.9 与 FR-8.12。LLM 输出跨供应商版本不可复现，"确定性"一词已从全部面向合规读者的表述中移除。审计所需的是**记录还原**（FR-8.9），它由 FR-8.1–8.3 免费提供，因此列为 P0。

| FR-9.4 | 提供 docker-compose 合成事故环境（Loki + Prometheus + 合成服务） | P0 |
| FR-9.5 | **合成事故场景必须需要多轮关联才能诊断**（例：下游依赖劣化导致上游连接池耗尽，表现为一组表面无关的超时） | P0 |

## 6. 非功能需求

### 6.1 只读保证的分层模型

> 这是全文最重要的一节，也是 P3 评审的核心。表述原则：**只承诺可证明的**。

| 层 | 控制 | 责任方 | 该层失效的后果 |
|---|---|---|---|
| **L1（主控）** | 最小权限凭据：agent 使用的服务账号在后端 RBAC 上不具备任何写权限 | **部署方组织** | 无。这是唯一的强保证 |
| **L2（纵深）** | 出站策略中介：主机/路径/方法允许清单 + 模板化查询构造（FR-2.x、FR-3.x） | 本工具 | 退化到 L1 |
| **L3（结构）** | 代码中不存在写路径；后端访问统一经受约束 client；CI 断言（FR-2.3） | 本工具 | 退化到 L1 / L2 |
| **L4（可选）** | 进程级出网允许清单：容器仅可到达声明的端点与模型端点 | 部署方组织 | — |

| ID | 需求 |
|---|---|
| NFR-S1 | 本工具不包含任何写路径代码。结合 L1–L4，写操作在多层被独立阻断。**本工具不主张单靠自身即可保证只读**（见 N7） |
| NFR-S2 | 快速开始文档与 README 必须将"为 agent 创建只读服务账号"作为第一步，并附各后端的具体配置示例 |
| NFR-S3 | 提供威胁模型文档，明确覆盖日志内容的 prompt injection 面及其缓解措施与残余风险 |
| NFR-S4 | 凭据仅从环境变量或密钥管理器读取，不落盘、不入日志 |
| NFR-S5 | 提供 SECURITY.md 与漏洞披露渠道 |

### 6.2 合规与可审计

| ID | 需求 |
|---|---|
| NFR-C1 | 任一历史运行可完整还原：执行了什么查询、取回了什么、推理输入输出为何 |
| NFR-C2 | 配置、策略、查询模板集、模型版本均可追溯至具体运行 |
| NFR-C3 | 支持数据完全不离开组织边界的部署模式 |
| NFR-C4 | run 目录的保留与销毁策略可配置且有据可查 |

### 6.3 可用性

| ID | 需求 |
|---|---|
| NFR-U1 | **规则式 Planner 的快速开始 ≤ 5 分钟**（README 三行命令，无需 API key、无需模型下载）；本地模型模式另行给出真实耗时 |
| NFR-U2 | 提供 Docker 镜像与 PyPI 包两种安装方式 |
| NFR-U3 | 配置为声明式 YAML，可纳入版本控制 |
| NFR-U4 | 失败时给出可操作的错误信息，含配置项定位 |

### 6.4 性能与成本

| ID | 需求 |
|---|---|
| NFR-P1 | 单次诊断端到端 ≤ 5 分钟（不含后端查询本身的耗时） |
| NFR-P2 | 单次运行的查询次数、返回数据量、Token 消耗、货币成本均有可配置上限 |
| NFR-P3 | 对被查询后端的调用可限流，且有全局并发上限，避免事故期间加重负载 |

### 6.5 可移植与运维

| ID | 需求 |
|---|---|
| NFR-O1 | Python 3.11+，无平台特定依赖 |
| NFR-O2 | 可在离线/受限网络环境部署（镜像自带依赖） |
| NFR-O3 | 语义化版本；CI 覆盖测试与 lint |

## 7. 约束与假设

### 7.1 约束

| ID | 约束 |

| CON-7 | v0.1.0 须在 2026-11-15 前公开 |

### 7.2 假设

| ID | 假设 | 若不成立的影响 |
|---|---|---|
| ASM-1 | 目标组织已部署可观测性后端并提供只读 API 访问 | 无此前提则无法取证，项目不适用 |
